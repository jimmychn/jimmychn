# 眼鏡連鎖店 POS 進銷存系統 - 標準開發與維護規格書

(Enterprise POS System Requirement & Development Specification)

## 1. 專案概述 (Project Overview)

本系統專為眼鏡連鎖門市量身打造，涵蓋完整的進銷存 (ERP) 與端點銷售 (POS) 功能。系統核心支援多門市、多商業類別與多層級權限控制，並整合從驗光處方、訂貨加工、銷售結帳到後續售後服務之完整眼鏡零售業務閉環。

## 2. 系統架構與技術基礎 (Architecture & Tech Stack)

### 2.1 核心技術選型

- **後端語言**：PHP (目前運行於 5.6)
  > [!WARNING]
  > PHP 5.6 已經於多年前停止官方安全維護，存在極大資安風險，並缺乏現代語法 (如 `??` 運算子)。強烈建議將未來架構與主機環境規劃升級至 PHP 8.x 系列。
- **資料庫**：MSSQL 2014 使用 PDO (PHP Data Objects) 驅動連接。
- **前端框架**：Bootstrap 5, jQuery。
- **介面設計**：RWD (Responsive Web Design) 響應式佈局，完美適配電腦、平板與手機操作。

### 2.2 技術開發規範與注意事項

- **SQL 分頁處理**：SQL Server 2012 起 (包含您使用的 2014 版) 已原生支援 `OFFSET ... FETCH NEXT`，建議檢查資料庫相容性級別 (Compatibility Level)，若設定正確即可直接使用，無須強迫依賴 `ROW_NUMBER()` 寫法。
- **PDO 參數綁定**：嚴格執行 Parameterized Query 以防範 SQL Injection。PDO `?` 位置參數為 1-based (需使用 `bindValue($key+1,...)`)，切勿與 PHP 陣列的 0-based 混淆。
- **統一 API 格式標準**：前後端分離架構中，每個前端功能 (`功能名稱.php`) 應搭配專屬資料處理 API (`功能名稱_api.php`)，強烈建議 API 全面採用標準化 JSON 格式回傳，例如 `{"status": "success", "data": [...], "message": ""}`，並將權限檢查列為必要攔截邏輯。
- **資料庫交易 (Transaction) 機制**：
  > [!IMPORTANT]
  > 所有涉及金流、庫存異動的單據確認與取消，**必須** 包裝在 DB Transaction 中 (`beginTransaction()`, `commit()`, `rollBack()`)，以防斷線或部分執行成功導致帳務或庫存發生不一致。

### 2.3 UI/UX 設計指引

- **導覽列互動**：
  - **桌面/平板版**：左側固定，黑底淡灰字，Hover 時背景深灰，Active 時藍底高亮。
  - **手機版**：頂部橫條下拉，選單單列排版。
  - **子選單**：支援展開收合操作，UX 設計需直覺流暢。
- **資料表格 (Bootstrap Table)**：支援欄位顯示隱藏 (記憶使用者習慣)、資料匯出 (Export)、以及分頁按鈕 (含中文的「第n頁/共m頁」和「上頁...下頁」)。清單群組需有深淺斑馬紋及 Hover 變色 (表頭為淺藍底色)。
- **輸入與對話框 (Modal)**：所有 CRUD (新增、檢視、編輯、刪除) 採用共用 DIV Modal 處理。版面要求全螢幕居中、可拖曳；欄位依大小自動分為 1~4 欄；日期欄位綁定日曆套件快速點選；具備關聯資料的欄位 (如商品、會員、門市) 須實作快速彈窗查詢並自動帶入主表單，Modal 視窗需有遮罩層防止點擊背景，如果顯示項目過多必須要加捲軸。

## 3. 核心業務流程 (Business Process Flows)

眼鏡業標準銷售與後勤生命週期：

1. **驗光 (Optometry)**：視力檢查，紀錄球面、散光、角度、加入度、瞳距、菱鏡角度、利眼、矯正視力及備註等多項專業數據，提供歷史對比，建立最終處方度數。
2. **承件 (Order Intake)**：客戶選購鏡框(A)、鏡片(B)、隱形眼鏡(C)、藥水(D)、耗材(E)。收取訂金 (支援現金、刷卡、數位支付、抵用券、點數折抵)，開立取件單與發票。
3. **訂貨與驗收 (Procurement)**：針對缺貨或需客製的商品 (如處方鏡片須加上染色、鍍膜、裁切、拋光、鑲鑽等特殊加工；隱形眼鏡依照處方度數挑選) 向上游廠商訂貨並進行入庫驗收。
4. **加工 (Processing)**：分派商品至委外或內部加工站點 (裁切、切溝、鑽孔、拋光等)。
5. **取件 (Delivery)**：客戶來店試戴，基於承件內容進行微調，結清尾款(支援多種支付及積點抵扣)，開立發票，並依照當前商品規則累積消費點數。
6. **售後服務 (After-Sales)**：提供鏡架調整、鏡片清洗、點數查詢與各項顧客關懷與回訪。

## 4. 系統模組與資料表規劃 (System Modules & Database)

系統具備完整的微型 ERP 架構，包含以下子系統模組 (每個模組皆對應 `*.php` 介面與 `*_api.php` 資料處理接口)：

### 4.1 系統權限與基礎架構 (Infrastructure & Security)

- **Programs (程式表)**：登錄程式代碼、名稱與各細項功能授權判定 (新增、檢視、修改、刪除、Search、Export、列印、流程作廢/回復/確定等權限卡控)。
- **Roles (角色表)**：維護9級權限編碼 (9管理者、8總經理、7區經理、6經理、5店長、4組長、3驗光師、2業務員、1工讀生)。
- **RolePermissions (角色權限表)**：設定各角色對各程式的具體操作授權細項。
- **Users (使用者管理)**：管理前端登入帳號與權限綁定。預設管理帳號 `admin/admin1234`，限制密碼禁止空白及低於 4 碼，帳戶不可刪除。嚴格規範密碼需使用 `password_hash()` 加密儲存。
- **登入與權限驗證 (Login & Authentication)**：
  - **權限攔截**：所有前端程式或後端 API 都需要檢查執行權限。若前端程式執行功能權限不足，則跳轉至 `Login.php` 重新登入；若執行後端 API 權限不足，則以 JSON 格式回覆權限不足的訊息。
  - **登入作業 (`Login.php` / `Login_api.php`)**：
    - 需輸入「門市代碼」、「使用者帳號」、「密碼」(密碼必須加密傳輸)、「圖形驗證碼」。
    - **登入成功**：開啟 `index.php` 進入系統主頁。
    - **登入失敗**：停留在登入畫面，並於畫面下方顯示累計登入失敗次數。
    - **防暴力破解機制**：同 IP 第 3 次登入失敗後，必須等 1 個小時後才可再嘗試登入；同 IP 累計第 5 次失敗後，該 IP 將被永久鎖定不得再登入！
  - **忘記密碼**：使用者點擊【忘記密碼】後，系統會於介面顯示並寄送一封具時間限制的密碼重設連結至其建檔的信箱中讓使用者改變密碼，信箱在畫面上需打碼隱私顯示 (例如 `a***n@example.com`)。
- **SystemLogs (系統日誌表)**：紀錄所有登入行為(不論成功或失敗，夾帶 `UserID`, `ShopID`, `AuthID`)、系統除錯及重要資料庫異常異動。

### 4.2 基本資料與屬性管理 (Master Data Management)

- **TAB / TABH (全域清單/類別維護)**：集中管理行業代號、會員等級、職業等系統跨介面全域下拉選單來源。
- **Stores (門市管理)**：管理總部與各加盟分店資訊、上下班時間、營業日及區域劃分。
- **Staffs (員工管理)**：記錄員工基本資料、所屬門市、各項聯繫資訊及入離職狀態。
- **Customers (會員管理)**：記錄客戶屬性。
  > [!IMPORTANT]
  > 個資保護規範：涉及客戶聯絡方式與過往配戴數據，應依循資安規範限制檢視權限與建立讀取 Log 日誌。
- **ZIP (郵遞區號表)**：提供地址輸入時的關聯選單。

### 4.3 零星庫存與商品管理 (Inventory & Product Management)

- **Products (商品基本資料)**：維護各類別商品共通屬性及定價策略 (支援進貨價、銷售價及廠商編號對照)。
- **ProductPromotions (商品促銷管理)**：虛擬商品包裝設定組合件，合併多項明細進行單體銷售及對應庫存扣減。
- **Stock (分店庫存/批序號管理)**：依據批序號 (含詳細處方屬性如：球面、散光、角度、加入度、弧度) 嚴格控制各分店獨特品項之庫存總量與進銷紀錄。
- **StockProcessing (批序號加工表)**：針對實體批序號掛載之特殊加工紀錄表 (染色、鍍膜、裁切等)。

### 4.4 採購與調撥管理 (Procurement & Transfer)

- **Invoices / InvoiceDetails (進貨/進貨明細)**：處理門市向廠商採購驗收之入庫作業。若為鏡片進貨，需於此步驟結合加工屬性與度數同步產生存貨紀錄。
- **InvoicePayments (進貨付款資料)**：對應採購之應付帳款與支付紀錄。
- **Transfers / TransferDetails (庫存調撥)**：處理跨門市之間庫存相互支援、轉移之流動單據。
- **TransferReceipts (調撥收款)**：與跨店調撥產生連動之帳務異動費用結清。

### 4.5 終端銷售與收銀管理 (Point of Sale)

- **EyeExams (驗光資料表)**：儲存專業配鏡處方檢驗數據及歷史軌跡。
- **EyeExamPayments (驗光收款)**：獨立或合併收取的驗光服務費用。
- **Sales / SalesDetails (銷售/銷售明細)**：支援標準表單與觸控條碼雙模式結帳；涵蓋商品列、小計、折扣優惠、稅金及最終應付金額計算。
- **SalesPayments (銷售收款)**：支援多模支付 (現金、刷卡、各種電子支付、票據、折讓與積點混合扣抵)。

### 4.6 財務與點數管理 (Finance & Loyalty)

- **積點管理**：嚴格控管每一會員的積點活動異動流 (包含新增、扣抵、作廢回補及有效期限)。
- **PettyCash (零用金管理)**：維持零星收支紀錄，如店面營運雜支、代墊廠商運費、日常水電雜項等。
- **Banks / BankAccounts / BankAccountTransactions (銀行管理)**：涵蓋銀行代碼、各門市分戶對帳單建立，及後效支票、刷卡請款入帳對帳管理。

### 4.7 報表與 BI 統計 (BI & Reports)

- 客戶促銷名單 (運用多條件如：年齡、消費習慣、品牌偏好、生日月等自動生成行銷短訊與名條投遞清單)。
- InvoiceStatistics (進收貨狀況追蹤報表)。
- TransferStatistics (店面流動調撥查詢與盤點報表)。
- SalesStatistics (營業績效、品牌業績、員工成效與個人單品獎勵核銷報表)。
- PettyCashStatistics (店面營運現金流量表)。
- AccountCardStatistics (非現金支付/帳卡清算統計)。
- ComprehensiveStatistics (綜合總帳報表 - 提供複合日結之應收、應付、零用金收支總覽，協助店長日終快速打烊對帳)。

## 5. 系統編碼規則 (Numbering Standards)

為確保跨門市運行的資料唯一性與辨識度，採用絕對自訂編碼原則，系統全域禁用流水號作為公開識別碼：

1. **門市代號**：自訂 10 碼 (程式邏輯處理時須自動去除頭尾空白)。
2. **員工編號**：門市代號 + 流水號(5碼)。
3. **會員編號**：門市代號 + 流水號(8碼)。
4. **單據編號 (Prefix + ShopID + Date + Sequence)：**
   - 銷售單：`S` + 門市代號 + YYYYMMDD(8碼) + 流水號(4碼)
   - 進貨單：`I` + 門市代號 + YYYYMMDD(8碼) + 流水號(4碼)
   - 調撥單：`T` + 門市代號 + YYYYMMDD(8碼) + 流水號(4碼)
5. **商品相關數位標籤**：
   - **商品類別**：`A`鏡框、`B`鏡片、`C`隱形眼鏡、`D`藥水、`E`耗材。
   - **品項代碼(SKU)**：[類別1碼] + [品牌6碼] + [原廠型號最大50碼] + [尺寸/容量1~4碼] + [顏色3碼]。
   - **存貨批(序)號編碼 (最高支援20碼)**：
     - 不強制編序號商品 (類別C, D, E)：直接採用外部廠商批號供查詢追蹤(可空白)。
     - 需綁定序號商品 (類別A, B)：強制限訂系統在進貨驗收時自動生成。編碼方式採用：`門市代號(去空白)` + `商品類別(1碼)` + `自動遞增流水號(8碼)`。

## 6. 系統交付與環境建置標準 (Deployment & Maintenance Guide)

1. **入口配置**：程式佈署由主控檔 (`index.php`)、登入驗證 (`Login.php`) 以及共用表頭與表尾 (`header.php`, `footer.php`) 發起。日後擴充新功能模組時，務必確保同步更新主菜單配置。
2. **單據狀態機與嚴密控管 (State Machine)**：
   - 銷售/進貨等單據應嚴格遵守以下防呆流程循環：`草稿(檢閱/編輯) -> 確認(正式扣減或新增庫存/帳目) -> (如需求) 授權倒轉作廢(自動回補庫存與資金) -> 結案歸檔。`
   - 一旦狀態跨出「草稿」，無論單頭單身均禁止任意新增、修改、刪除操作。
3. **版控與環境建置**：建議專案強制加入 Git 版本控制 (Version Control)，並區分為測試站 (UAT) 與正式站 (Production)。
4. **災難備援 (Disaster Recovery)**：MSSQL 須設定每日系統全備份策略 (Full Backup) 並搭配日誌檔定期備份 (Transaction Log Backup) 定期排程歸檔，確保意外情況下的資料可追溯性。
